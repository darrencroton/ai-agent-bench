# AGENTS.md

Guidance for AI coding assistants (Claude Code, Codex CLI, and equivalents) working in this repository. `README.md` is the user-facing entry point; this file is the contributor contract.

## What this repo measures, and what you are doing in it

This bench measures the Developer seat of a real `project-manager` Mode B run: which local model produces good code, and how many supervised iterations it needs to get there. **You are working on the measuring apparatus, never inside the thing being measured.** Adding a task, fixing a tool, extending the scoring sheet is ordinary software engineering on the harness. Never help a run along, never re-run a graded attempt and record it as the same one, never hand-edit a scoring sheet.

## The boundaries that make the measurement valid

- **Everything this repo does to a PM run is read-only.** Read `run.json` and `events.jsonl`; never write PM state, never hold or ask for a run token, never invoke `pm.py` as a subprocess. `pm_lib` is imported as a library for its plan and git helpers, nothing more.
- **Nothing is added to PM's launcher prompt, and PM is never asked to cooperate.** The premise is a completely normal, unmodified Mode B session; an instruction added to make measurement easier is an observer effect on the exact variable being measured. The operator launches PM personally — this repo has no code path that launches it, deliberately. `tools/cohort_run.py setup` only ever *prints* that unmodified prompt (extracted read-only from `project-manager`'s own `SKILL.md`, never a hardcoded copy that could drift stale) so an operator has nothing to hand-assemble — it must never itself invoke `pm.py`, spawn a session, or write into a Developer/PM directory. If `SKILL.md`'s own launcher wording ever changes, `setup` picks that up automatically on its next run; it is never edited here to match. `setup` *does* create a fresh git worktree of the substrate repo (the resolved task's configured `repo` in `policy.yaml`'s `tasks:` registry — for `relative-velocity`, a local clone vendored under this repo's own gitignored `substrate/` for self-containment — see policy.yaml's own comments) so the printed prompt's `Repo:`/`Plan file:` are already correct — this is not the same thing as launching PM or cooperating with it: it is ordinary git housekeeping on a repo that is its own independent git checkout, untracked by this one, happening entirely *before* any PM run exists, the same preparation an operator would otherwise do by hand. `cohort_run.py cleanup` removes that worktree afterward (never its branch); it must never be extended to touch anything inside a live or historical PM run itself. `cohort_run.py analyze-all` batches `analyze` across every worktree `cleanup` would also see, discovering ungraded run directories (a directory listing plus reading `run.json`'s own `run_id`, nothing more) and calling `grade_run.py`/`model_report.py` per run exactly as `analyze` does one at a time -- it adds no new read of PM state and no new write path; a run still in progress is safely skipped because `grade_run.py` itself already refuses to grade one, not because `analyze-all` checks status first. `setup --harness <...>` additionally does a best-effort, atomic, merge-only write to that harness's own on-disk trust/permission store (never PM's or the Developer's state) so its first-launch prompt doesn't fire for a brand-new trial directory — a failure there is reported, never allowed to stop `setup` from creating the worktree and printing the prompt. `setup` also best-effort pre-builds the Developer repo's own `venv/` by running its `setup.sh` once, here, on the operator's own machine, before any PM run exists — the same "ordinary preparation an operator would otherwise do by hand" as the worktree creation above, never a live-run intervention. This exists because a Developer harness's own sandbox is not guaranteed to have working python3/network access to build one itself, which would otherwise leave its own "tests passed" claims unverifiable; pre-building it once on the one machine that always has both removes that dependence. A failure here is reported the same way, never allowed to stop `setup`.
- **Grading happens in a disposable worktree**, never PM's, the Developer's, or a reviewer's directory — and always after the whole run PM is supervising has finished. Never grade a slice while its own run is still in progress: not just because `grade_run.py` already refuses to, but because a live Developer session could otherwise discover the grading worktree's path (hidden tests included) via `git worktree list` in its own repo. This is a real, closed boundary today specifically because grading is always post-hoc — do not build a live-grading path without re-deriving this isolation argument first.

## Working on the tools

- **Every path, threshold and tunable lives in `policy.yaml`**, never hardcoded in a script. A policy change must not require a code change. Do not invent scoring weights outside it.
- **Task configuration lives in `policy.yaml`'s `tasks:` map and resolves exactly once, at the boundary.** Each entry (keyed by operator-chosen task id, with top-level `default_task` naming the fallback every tool applies when no `--task` flag is given) carries everything task-specific — target repo, branch prefix/worktree root, plan/provenance paths, hidden-tests dir, obligations file, expected slice count, measurement globs — and every tool resolves it through `bench_lib.resolve_task`, which validates the registry's own shape unconditionally (non-empty mapping, string keys, `default_task` naming a configured entry) and the resolved entry itself in full, failing loudly naming the task id and any missing or malformed key, never guessing. The resolved `task_id` then becomes a permanent structural fact: `dev_check.py` stamps it into each attempt's provenance at grading time (the only place task configuration is resolved against a real grading worktree), `model_report.py` propagates it onto `model-report.json`'s top level — backfilling it to `default_task` for sheets with no recorded `task_id` and marking those reports `task_id_source: "backfilled"` so the inference is always visible, never silent — and nothing downstream ever re-derives it: `grade_run.py`/`dev_check.py` take the explicit `--task` they were handed, and `leaderboard.py` partitions reports by their recorded `task_id` before any aggregation runs. Grading and leaderboard scoping is therefore per-task *by construction*, not by convention: one task's numbers can enter another task's tables only via a deliberately misconfigured registry, and even an operator-supplied but wrong `--task` is caught because `dev_check.py` cross-checks the run's own recorded repository against the resolved task's configured repo and refuses loudly on mismatch rather than silently grading under the wrong rubric. `leaderboard._check_correctness_provenance_consistency` compares only the three hash keys (`plan_hash`, `obligations_hash`, `hidden_tests_hash`) when checking that ranked reports were graded under one rubric, never the per-slice `task_id` echo or any other field on the block, because that echo legitimately differs across a tree that mixes sheets with and without a recorded `task_id` and must never read as a rubric disagreement.
- **Fail loudly and specifically.** Every error names the concrete file, path, node id or parameter. Never silently degrade, never guess a missing value, never write a partial result as if it were complete. An unavailable linter is recorded as unavailable, never as a clean pass; an unparsable review report is a named parse error, never zero findings.
- **Recompute what PM does not persist; reuse what it does.** The floor check's per-fact evidence is never written in structured form, so scope discipline is recomputed via `pm_lib.plan.effective_authorized_files` — the same function PM's own floor calls. Grants and reviews *are* structured and authoritative in `run.json`; read those rather than deriving a parallel copy. PM's own attempt counter is authoritative too, but only as a *live* snapshot — `run.json` never persists what it read at an earlier, now-superseded attempt, so grading one historically recomputes it from `events.jsonl` instead (`bench_lib.epoch_start_ordinals`), provably identical to PM's own counter rather than an invented parallel value — recorded on the attempt entry as `pm_attempts_counter` for cross-reference, never used as the sheet's key.
- **Grading is post-hoc, not live — a slice's `before_head` and a review's `head` are permanent, structural facts, recoverable from `run.json` alone once a run is finished (see `dev_check.resolve_before_head`'s docstring for the exact resolution order).** Do not reintroduce a live watch loop, polling, or a "grade at every floor event" contract without re-deriving why that's unnecessary: both facts are structurally recoverable from `run.json` alone, with no live state needed. A review report is still read only after verifying its recorded sha256, because the mirrored copy is written non-atomically — that remains a correctness requirement, not an optimisation.
- **Attempt numbering is a monotonic ordinal derived from `events.jsonl`, never `run.json`'s own `attempts` counter** (`tools/bench_lib.attempt_ordinal`, one implementation both tools call) — 0 on the initial launch, +1 per subsequent `launch`/`relaunch`/`steer` event for the slice. PM's own counter looks 0-based the same way but resets to 0 whenever a stopped slice is relaunched (`pm_lib.slice_ops.start_slice`'s non-relaunch branch), so it cannot be the sheet's key without overwriting an earlier attempt's row; it is still recorded on the attempt entry as `pm_attempts_counter`, for a human cross-referencing PM's own output. A tool that quietly used a different derivation, or a 1-based index, would leave the scoring sheet silently incomplete or overwritten rather than raising anything.
- **Minimum, no dead code.** Every file and function must be load-bearing. No speculative abstraction, no config key nothing reads, no compatibility shim for a case that cannot occur. Prefer one parameterised script to two near-identical ones — that is why the drift-audit and code-review harvesters are a single tool.
- **Deterministic first.** Scores come from tools that produce the same answer twice. A subjective signal (PM's own comparative rating of its reviewers) may be surfaced, labelled as such, but is never blended into a deterministic number: the two differ in repeatability, and averaging them destroys that distinction silently.
- **Never default a commit to "whatever HEAD currently is."** A non-accepted slice's ending commit is not structurally recoverable — a top-level `pm stop` can end an attempt with no floor check and no commit recorded, and a stopped run can be reactivated later — so grading one always refuses rather than guessing. Only an accepted slice's `entry["commit"]` (or a review's `head`, matched exactly) is ever safe to resolve automatically.
- **One failure must never silently discard another attempt's data.** `review_score.run_review_score` processes each of a slice+skill's review commissions independently; a missing sheet row for one attempt is a reported, recoverable problem, never a reason to abort before reaching a later attempt that does have a row. Any change to that loop must keep every attempt's outcome independent of every other's — a superseded attempt's missing row must never silently discard a later, gradeable attempt's own review data.
- **One record per review commission, never one slot per role.** An attempt's `reviews` list holds one record per successful commission, keyed on its `events.jsonl` index (`review_id` is carried for PM's judgment join but is only unique *within* a slice, and some runs have none at all). Two reviewer models on one submission are a panel: both records stand. A re-commission of the *same* reviewer — same `(skill, tool, model, effort)` lineage — is a retry: the earlier record stays, marked `superseded_by`, so a retry never earns a second vote and a failed review never vanishes. `open_after_this_attempt` carries over per lineage, never per skill alone; mixing two reviewers' findings into one survival count would be meaningless.
- **PM's own judgments are surfaced, never blended.** `review_judgments`/`developer_judgments` are read through `bench_lib.active_judgments` and joined structurally — reviewers by `(run_id, slice.id, review_id)`, the Developer by `(run_id, slice.id, submission.origin_event.index)` converted to the bench's own attempt ordinal — never by list position, model, or artifact content. They are displayed in their own labelled columns and tables, exactly as `pm_subjective_rating` already is, and enter no deterministic number. An attempt or review PM never rated is *explicitly unjudged*: `pm_lib` refuses historical backfill by construction, so a gap there is a real gap and is never inferred.
- **Test kill rate is a second, independent ranking, never a component of correctness.** `dev_check.measure_test_kill_rate` runs the Developer's *own* test files (the task's `test_paths` globs over the files tracked at the graded commit, never the hidden tests: the gate has its own disposable worktree, which the hidden tests never enter and whose leftovers never reach the worktree they are graded in) once unmutated, once more as a control with the bank on `PYTHONPATH` and `MUTATION` unset, and then once per mutant the slice's `slice<N>.txt` lists, serially by default (`mutation_gate.parallel_workers`); a mutant is killed only when a node that passed unmutated stops passing. An errored run (a crash, a timeout, a collection error) is recorded as errored and counts against the rate — never as a kill, and never by shrinking the denominator. The bank's identity (`bank_hash`, per slice) rides on the measurement block itself rather than in the attempt's never-rewritten provenance, and `leaderboard.py` refuses to put two bank versions in one table exactly as it refuses two rubric versions. `Rank by test kill rate` orders nothing but itself: correctness keeps the primary rank and the row order, and the two are never combined.
- **The hygiene census and the process columns are descriptive and never scored.** `dev_check.measure_hygiene` counts, over the attempt's added production lines classified by the same per-line labelling `classify_source_lines` sums, how many comment and docstring lines match the narration patterns `policy.yaml`'s `hygiene:` block lists, plus commit-subject length and process-label counts over the attempt's own commits; `model_report.resolve_run_process` counts floor failures (a `floor` event whose note starts with `failed`) and nudges (`send` events) from `events.jsonl`. They sit beside ΔLOC as supporting columns and enter no rank; the pattern lists are policy, not code.
- **The quality panel is a model's judgement, collected post-hoc, and is kept apart from every deterministic number.** `tools/quality_panel.py` commissions one fixed read-only reviewer configuration (`policy.yaml`'s `quality_panel:` block) through the `orchestrator` skill's launcher against a disposable worktree of an accepted commit — never the Developer's directory, never during a run, never with the hidden tests present — and appends one record per commission to the attempt's `quality_panel` list, carrying the reviewer's tool, model and effort, the rubric's and the rendered prompt's sha256, and the five 1–5 scores with their evidence. A repeat commission is a second record, so the panel's repeatability is visible rather than averaged away; a malformed answer writes nothing. The scores are rendered in their own labelled table, headed as a model's judgement, and enter no correctness, kill-rate or ranking number.

## Working on the hidden tests

- **The obligation partition in each task's obligations file (`hidden_tests/obligations.yaml`, `hidden_tests/bench-multitask/obligations-{3,2}slice.yaml`) is the rubric weight.** Correctness is the equally weighted mean of the groups, so grouping decisions are weighting decisions. Balance by obligation importance, never by test or node count. `docs/OBLIGATION-GROUPS.md` records every task's partition and its reasoning, one section per task; record any change there with the evidence that prompted it. The two bench-multitask maps share one hidden-test directory and must stay identical over slices 1–2: edit both together.
- **Re-validate after any change to the tests or the map**, in both directions: every collected node in exactly one group, no group naming a test that does not exist. `dev_check.py` enforces this and fails loudly on any mismatch — an unmapped, doubly-mapped, or missing node stops grading rather than scoring a partial map. This is deliberately strict: a stale map that were allowed to pass silently would read as a permanently low ceiling across many runs, discovered much later — exactly the failure mode this check exists to prevent.
- **Validate a changed hidden test against a reference implementation before trusting it.** A wrong hidden test fails every model through no fault of its own, and one trial will not reveal it. `docs/reference-impl/README.md` has relative-velocity's reproduction recipe; `hidden_tests/bench-multitask/README.md` has the second task's, where the reference is this repository's own `main` at `310ab63` and the two red checks are the `multi-task-support` and `multi-task-support-2` branches. A test that fails the reference is wrong; a test that passes both red checks and the reference is not discriminating and needs a stated reason to exist.
- Every slice directory of a task contains a `test_hA.py`; a single pytest invocation over two slices fails collection. Grade one slice per invocation.

## Working on the mutation banks

- **One mutant, one obligation, applied to a plan-named public function after import.** A task's bank (`policy.yaml`'s `mutations_dir`: `sitecustomize.py` plus one `slice<N>.txt` per plan slice) is loaded by the interpreter at startup when its directory leads `PYTHONPATH` and `MUTATION=<id>` is set; it matches modules by basename so a candidate's import style cannot dodge it, hooks `builtins.__import__`, `importlib.import_module` and `importlib.reload`, and leaves a mutant *uninstalled* (survived) rather than crashing every run when the candidate lacks the function it wraps. A transform or install failure propagates loudly: a broken mutant is never evidence that a suite survived it. Nothing in a bank ever edits a trial file, and no bank is ever part of a task's substrate.
- **Every mutant is validated against the task's reference before it is trusted, and recorded in that task's reference README.** The reference implementation's own suite must kill every mutant under the slice that lists it (a survivor is mis-slotted, equivalent, or a reference-suite gap: investigate, never drop silently); a deliberately weak suite must kill few; the frozen pre-plan suite must kill none; `MUTATION` unset must change nothing. Re-run that recipe after any change to a bank or its slice lists, and expect the per-slice `bank_hash` to change — a changed bank is a new measurement version, and `leaderboard.py` will refuse to mix it with sheets graded under the old one until the cohort has been graded again under it.
- **The slice lists partition the registry.** `tests/test_mutation_banks.py` checks every configured task's bank: the hook installs nothing when `MUTATION` is unset, every listed id is registered, and every registered id is owned by exactly one `slice<N>.txt` in the directory (a bank shared by plans of different lengths is counted over every list it holds). A registered mutant no list owns would never be measured; one owned twice would count under two slices.

## The vendored plans are frozen

`docs/MERGER_RATE_PLAN-2SLICE.md` is a pinned copy from `relative-velocity` (see its `.provenance.md`). Do not edit it, and do not silently re-vendor it — a change there changes what is being scored mid-cohort. A defect found in its text is documented, not patched: one such defect is already recorded in `docs/reference-impl/README.md`, along with why the corresponding hidden test was deliberately left as it is rather than edited to match a self-contradictory bullet.

The same rule governs `docs/plans/MULTI-TASK-PLAN-3SLICE.md` and `docs/plans/MULTI-TASK-PLAN-2SLICE.md`, pinned copies from the `bench-multitask` substrate (see their `.provenance.md` files); a defect found in either is recorded in that task's reference README (`hidden_tests/bench-multitask/README.md`, written together with its hidden tests), never patched. A plan the PM is handed must read as a stand-alone plan for its own repository: bench-side history — what was cut from an earlier plan, which run found a defect, how the plan was validated — lives in the provenance file, never in the plan text, so the Developer and reviewers see nothing a normal, unmeasured run would not. `docs/MERGER_RATE_PLAN-2SLICE.md`'s own provenance paragraph predates this rule and stays, because stripping it mid-cohort would be a new rubric version; apply the rule to it only as part of a deliberate re-vendor.

The calibration record for a task's hidden tests is kept with the tests, never in the plan: `hidden_tests/bench-multitask/README.md` records that the plan's conditional criteria which read the operator's real `results/runs/` tree (Slice 2's prior-sheet regrade equivalence, Slice 3's historical backfill) are covered by fixtures in a trial worktree, where that tree does not exist — a recorded design decision, not a plan defect.

## Conventions

- **Archive, never delete.** Superseded files move to a dated directory under `archive/` (gitignored). This is not decoration: a gitignored file has no git history to fall back on if it's removed outright. Run `git clean -ndx` first to see what is untracked before removing anything.
- **Style** follows the `style-guide` skill's baseline: `snake_case`, test names describing behaviour, docstrings where the contract is not obvious, `Path` over string paths, CLI parsing confined to `main()`, comments explaining contracts and non-obvious choices rather than restating code. Markdown prose is never hand-wrapped.
- **Lint before committing** — the `lint` skill (`ruff`/`markdownlint`/`codespell`). It must be clean, not merely improved.
- **Fold a design decision into this file (or the relevant code's own docstring), not only into a local session log.** A resolution recorded only in a gitignored, machine-local note leaves no trace for a fresh clone. This file and the code are the authority; any such log is a local aid, never the record of a decision.
