# Design: PM-Only Evaluation

**Status:** All five scoring tools are built, tested, and validated against a real completed PM run: Tools 1-3 (`tools/dev_check.py`, `tools/review_score.py`), the grader (`tools/grade_run.py`), Tool 4 (`tools/model_report.py`), and Tool 5 (`tools/leaderboard.py`). G16 (§8) — grading every attempt, not just each slice's final one — is resolved via the git-log walk. A sixth, operator-convenience tool, `tools/cohort_run.py` (§6), wraps `setup`/`analyze`/`cleanup`/`reset-leaderboard` around the five scoring tools without adding any new measurement — it never launches PM. The tool suite is complete. The leaderboard rebuild (`docs/LEADERBOARD-REBUILD-PLAN.md`) has landed stages 1–4: Developer identity resolved structurally, the saturated composite deleted in favour of mean first-attempt correctness, ΔLOC/ΔCC replacing the vacuous quality verdict, and panel-preserving review records plus PM's own judgments. Stage 5 (regrade the eight-run cohort and close out) is outstanding; see `HANDOFF.md` for exactly where a fresh session should pick up.

This document describes what the system is and how it works. For how it got this way, see the History appendix at the end — read it only if you need the reasoning behind a specific decision.

## 1. What this measures

Which local model should sit in the Developer seat of a real, supervised `project-manager` Mode B run on production scientific code? Local models tend to converge on scientifically equivalent code but differ sharply in final quality and in how many review/fix iterations it takes to get there. That variance is the thing worth measuring, repeatably and offline — not by using a model "in the wild" and hoping.

The method: run a real, **completely normal, unmodified** `project-manager` Mode B session against a frozen two-slice plan (`docs/MERGER_RATE_PLAN-2SLICE.md`, vendored from `relative-velocity` at a pinned commit), with the candidate model in the Developer seat. Once the run is finished, grade it from PM's own artifact trail — correctness against held-out hidden tests, independently measured code quality, scope discipline, and every commissioned reviewer's findings — for every attempt of every slice that a git-log walk can recover (§5), falling back to just the final attempt only where it can't. This is a *trajectory*, not just an end state: how many attempts a slice took, and what each reviewer found, are as much the measurement as the final code's quality.

## 2. Design principles

- **The PM session is never instrumented, wrapped, or told anything about this bench.** The operator launches it exactly as they always do (`project-manager`'s own `SKILL.md` launcher prompt, unmodified, every field filled in normally). Anything that made measurement easier by changing what PM does would contaminate the thing being measured.
- **Everything this repo does to a PM run is read-only.** No run token, no writes to PM state, `pm.py` is never invoked as a subprocess — `pm_lib` is imported as a library for its plan/git helpers only.
- **Deterministic first.** Correctness and quality are measured by tools, not by asking a model to judge a model. An LLM judge is a fallback for if a deterministic proxy proves insufficient, never a default.
- **Externalize policy as data.** Every path, threshold, and tunable lives in `policy.yaml`. A policy change must never require a code change.
- **Fail loudly, never guess.** An unavailable linter is recorded as unavailable, never as a clean pass. A base commit that cannot be safely resolved is a named, refused grading target, never a silent default to whatever HEAD happens to be. A stale sheet, a mismatched run, a partial review report — every one of these is a named error, never a quiet zero.
- **Minimum, no dead code.** Every file is load-bearing. A prior repo's useful *pattern* (fail-closed scope checks, provenance hashing) is reimplemented fresh and small, never carried over wholesale from code written for a different purpose.
- **Grading is isolated from the PM/Developer run.** Every grading pass checks out the commit under test into a fresh, disposable git worktree — never PM's or the Developer's own working directory.

## 4. How a run works, end to end

1. **The operator launches PM** — a normal Mode B session, `SKILL.md`'s unmodified launcher prompt, with the candidate model in the Developer seat. This repo never launches it, and never adds anything to that prompt. `python tools/cohort_run.py setup` creates a fresh trial worktree of `policy.yaml`'s `relative_velocity_repo` (a local clone vendored under this bench's own `substrate/`, gitignored, so trials never depend on the operator's own working checkout elsewhere; checked out from this bench's one pinned plan commit, on its own `pm-eval-v2/<label>` branch) and prints that exact prompt (extracted live from project-manager's own `SKILL.md`, never a hardcoded copy — see §6's Tool 6) with `Plan file:`/`Repo:` already filled in, plus these same steps, so there is nothing to hand-assemble or hand-type. `Developer:`/`Reviewer:` are left exactly as the template states them — who plays either seat is the operator's own choice, typed in by hand when the prompt is pasted; this tool carries no flag for either. `--repo <path>` skips worktree creation and uses an already-prepared repo instead.
2. **PM supervises the run to completion**: Developer sessions per slice, reviews it commissions on its own judgment (often a panel of several reviewer models, harvested per-review by Tools 2/3 — §6), and accept/steer/stop decisions, exactly as an ordinary Mode B run.
3. **Once the run is finished** — `run.json["status"]` is `complete`, or `stopped` with PM's own closing event on record; `needs-human` is a pause, not a finish — grade it, build its per-model report, and refold the cross-model leaderboard in one command:

   ```bash
   python tools/cohort_run.py analyze --run-dir <pm-run-dir>
   ```

   `<pm-run-dir>` is PM's authoritative run directory, `<worktree-git-dir>/pm/<run-id>/` (find it with `git rev-parse --absolute-git-dir` in the Developer's repo — the in-worktree `.pm/` copy is a mirror, not the authority; `--dev-repo <dev-repo>` does that resolution for you when exactly one run exists under it). `analyze` is `grade_run.py` → `model_report.py` → `leaderboard.py`, run as three in-process calls, in that order; each step's own refusal is reported without aborting a later step that can still proceed. Equivalently, the same three tools can still be run by hand, one at a time (below) — `cohort_run.py` adds no new measurement, only sequencing. `grade_run.py` refuses to run against anything that isn't confirmed finished.

   ```bash
   python tools/grade_run.py --run-dir <pm-run-dir>
   python tools/model_report.py --run-id <run-id>
   python tools/leaderboard.py
   ```

4. **Who runs step 3, and when, is the operator's call** — not fixed by this design. The operator can run it themselves the moment PM reports done, or separately tell the same or a fresh PM/agent session, once the plan is finished, to read this repo's instructions and run it. Both are fine: the tool doesn't care who invokes it, only that the run is actually over. (This is a different question from "should PM invoke bench tooling *while* supervising" — that stays rejected, for the same reason PM's prompt is never modified: it risks contaminating the judgment being measured. Running a read-only report *after* every decision is already locked into `run.json` carries no such risk.)
5. Check `results/leaderboard.md` (the human-readable ranking plus each model's own per-slice detail; `results/leaderboard.json` carries the same per-model ranking for machine use, not the per-slice detail). Once a trial's worktree is no longer needed, `python tools/cohort_run.py cleanup` removes it (never its branch; dry run by default, `--yes` to actually remove, an ungraded trial flagged with a warning rather than refused). Separately, `python tools/cohort_run.py reset-leaderboard` archives (never deletes) `results/` itself, for starting a whole cohort pass over clean.

## 5. Grading design: a single pass over a finished run

Grading happens once, after the run is over — not by watching PM live. This is correct, not just simpler, because the two facts that matter are both permanent and structural, recoverable from `run.json`/`events.jsonl` alone with no live state needed:

- **A slice's `before_head`** (the commit correctness/quality/scope are measured against) is set once, at `start_slice`, and preserved unchanged across every relaunch/steer within one uninterrupted in-flight epoch (`pm_lib/prompts.py`; verified against `pm_lib/slice_ops.py`'s `start_slice`). It is not permanent across a stop-then-restart of the same slice, which captures a fresh value — `dev_check.resolve_before_head` (below) accounts for this.
- **A slice's ending commit**, once accepted, is permanently recorded (`run.json`'s `entry["commit"]`, set by `finalize_accept`). Mode B processes slices strictly in plan order and gates progression on acceptance (or an operator's `--attest`), so at most one slice in a finished run can be non-accepted, and only if it's the last one PM ever touched.

`tools/dev_check.py`'s `resolve_before_head` resolves the base commit in this order, each one cheaper/more authoritative than the next:

1. An explicit `--before-head` override, if the caller supplied one.
2. `current_slice.before_head`, if this slice is still live (only relevant when grading manually, mid-run).
3. This attempt's own previously recorded `provenance.base_commit`, if it was graded before.
4. Structurally, from `run.json` alone: the immediately preceding slice's recorded `commit` (for any slice past the first, if that predecessor was actually run through PM and accepted — an `attested`, operator-approved predecessor never records a commit and falls through to the next option); or, for any slice including the first, the most recent review commissioned against it whose `head` matches this slice's own recorded accepted commit — a guarantee, not a heuristic, because reviews record the exact commit they ran against and this bench's plan mandates a fresh review before acceptance. (Recency by list position alone is *not* used for an accepted slice: reviews commission concurrently, and a slow, earlier-epoch review's report can be parsed and appended after a faster, current-epoch one — filtering by exact `head` match avoids that race entirely.)

`tools/grade_run.py` uses this to grade every slice in one pass:

- Refuses to run unless `run.json["status"]` is `complete` or `stopped` *and* PM's own closing event for that status exists anywhere in `events.jsonl` (not merely as the most recent tracked event — PM saves status before appending the matching event, and an unrelated trailing event, like a routine `stop` issued after a run already completed, must not mask an earlier real closing event).
- For each slice, resolves its final attempt's ordinal from `events.jsonl` and its ending commit: an accepted slice's recorded `commit`; a non-accepted slice is always refused (never defaulted to the repo's current HEAD) — a top-level `pm stop` can end an in-progress attempt with no commit recorded and no clean-worktree guarantee, and a stopped run can be reactivated later, so nothing about "current HEAD" is safe to assume for that case. Grade a stopped, non-accepted slice by hand with `dev_check.py --commit <sha>` once you've independently confirmed the right commit.
- **G16, resolved — grades every attempt, not just the final one**, via `_resolve_attempt_grading_plan`/`resolve_attempt_commits` (`tools/grade_run.py`): git history is permanent and continuous across any PM-level "epoch" boundary (a `finalize --stop` followed by a later restart), so walking `git log --reverse` between a slice's own before_head and its final commit recovers one ending commit per attempt, in order, one commit per attempt-family event recorded in `events.jsonl`. That before_head is this slice's *original* one — the previous slice's own recorded commit, when one exists, not whatever `resolve_before_head` would return for grading a single already-decided attempt (which deliberately favors the most recent epoch, and would silently truncate a multi-epoch slice's walk to just its last epoch). This relies on the Developer contract's one-commit-per-attempt convention, not a mechanical guarantee `pm_lib` enforces, so the walk is a named refusal whenever it doesn't hold exactly (a merge commit in range, a `before_head` that isn't an ancestor of the final commit, or a commit count that doesn't match the attempt count) — never a partial or guessed mapping. A slice whose walk refuses falls back, on its own, to grading only its final attempt (the pre-G16 behavior), with the refusal reported as a named problem, never silently.
- Harvests every commissioned review for every attempt found in the event log — every one of which now typically has a sheet row to attach to, not just the final attempt's.
- Is fully idempotent — safe to re-run any time, including immediately, if in doubt about a narrow timing edge in the terminal-status check above.

**Residual scope limit (G16's honest edge):** a slice whose commit history doesn't satisfy the walk's one-commit-per-attempt convention exactly still gets only its final attempt deterministically graded (hidden tests, lint, code-health, scope) — most commonly a multi-epoch *first* slice (no predecessor's commit to fall back on for its walk-start, and `resolve_before_head`'s own rule for an accepted slice only ever returns the most recently-accepted epoch's before_head, never an earlier one, *even when a review from that earlier epoch was recorded* — a first slice that itself restarted always falls back here, not just when its earliest epoch went unreviewed), or any slice where the Developer's own commit-per-attempt convention didn't hold. A review commissioned against an attempt with no sheet row is still reported as a named, loud problem when harvested, never silently dropped. The attempt *count* and PM's per-attempt *decision* (steer/accept/stop) are unaffected by any of this — both come from `events.jsonl` directly, for every attempt, regardless of which ones got a deterministic grade.

**Per-attempt fidelity within a slice:** `before_head` is constant across every attempt sharing one PM "epoch" (a `launch` through the `relaunch`/`steer`s that follow it, before the next `launch`), resetting only at the next epoch's own start — not, as an earlier draft of this walk incorrectly assumed, advancing to the immediately preceding attempt's own commit on every attempt uniformly. That incremental assumption was caught (by an independent review round, then verified against the real completed run's own regenerated sheet before this was written) as a real bug: it would silently miss a scope violation or quality finding introduced early in a slice and left untouched by a later attempt, since nothing changed in that specific incremental diff. PM's own `pm_attempts_counter` is not constant within an epoch — it increments by 1 on every attempt, same as before — but it resets to 0 at exactly the same epoch boundary `before_head` does, so both are governed by the one `bench_lib.epoch_start_ordinals` helper, which derives each attempt's epoch boundary directly from `events.jsonl` (PM's own counter resets/increments in exact lockstep with the same launch-family events, verified against `pm_lib.slice_ops.start_slice`/`steer`). `tools/grade_run.py`'s per-attempt `before_head` and `tools/dev_check.py`'s `resolve_pm_attempts_counter` are both built on it.

## 6. The tools

### Tool 1 — `dev_check.py`: correctness, quality, scope for one attempt

A pure, one-shot grading command: given a run directory, a slice number, and (optionally) an explicit attempt/commit, it checks that attempt's commit out into a disposable worktree, copies in that slice's held-out hidden tests, runs them, and scores them per acceptance-obligation group (`hidden_tests/obligations.yaml` — the partition *is* the correctness rubric; see `docs/OBLIGATION-GROUPS.md`). It then measures quality independently — invoking the `lint` and `code-health` skills directly, never trusting whatever PM's own prose assessment happened to mention — records **production size and complexity** (ΔLOC and ΔCC, below), and recomputes scope discipline by calling `pm_lib.plan.effective_authorized_files` directly, the same function PM's own floor check uses. Every tool that inspects the worktree runs *before* the hidden tests are copied in — the differential `--base` invocations and the absolute `analyze --all` one all see untracked files, and would otherwise attribute this bench's own test files to the Developer.

**ΔLOC and ΔCC** (`docs/LEADERBOARD-REBUILD-PLAN.md` Stage 3) are both measured against *that slice's own `before_head`*, never the preceding attempt — a trajectory against a moving base would hide a regression introduced early and never touched again. ΔLOC is net physical lines from `git diff --numstat --no-renames`, with every changed path classified in Python against `policy.yaml`'s `measurement` globs (never a git pathspec, whose `**` semantics need `:(glob)` magic); production, test, doc and unclassified are separate buckets and test/doc are never netted against production, and a binary file's unmeasurable `-`/`-` counts are listed, never coerced to 0. ΔCC is total production function cyclomatic complexity at the endpoint minus the baseline, summed over every function `health.py analyze --all` reports at each revision — deliberately **not** from its `candidates` list, which is capped at `limit_per_family` and omits removed functions entirely, so counting it would turn a display cap into a scoring ceiling. The baseline measurement is cached per `(repo, before_head)` for the life of one grading process, since a slice's baseline is constant across its epoch. **ΔCC is descriptive and never scored**: splitting one function into three raises the total through added function-entry counts alone.

**Stage 4 addition — production ΔLOC decomposition (`dev_check.decompose_production_categories`).** Physical ΔLOC above conflates "wrote more code" with "wrote more docstrings, comments or blank lines" — a real fitness review found one Developer configuration reading 63% larger on the printed means purely because it wrote docstrings the other configuration did not. `size_complexity.loc` gains a `production_categories` block that reclassifies the **production bucket only** (never test or doc — the need this responds to is judging economy of implementation, not of tests or prose) into `code`/`docstring`/`comment`/`blank`, at both `before_head` and the endpoint commit, via `ast` (to find each `Module`/`ClassDef`/`FunctionDef`/`AsyncFunctionDef`'s first-statement docstring, and *only* that — a string constant anywhere else in a body is code) plus `tokenize` (to classify everything else, with code taking precedence over docstring taking precedence over comment on any line carrying more than one). This is asserted to reconcile exactly: the four categories' nets always sum to the same production net that `compute_loc_delta` already derived from `--numstat`, and a mismatch is a loud, named failure, not a quietly wrong number. A binary or unparsable production file makes the whole block `unavailable` with a named reason — never zeros — but never aborts the rest of grading, since a Developer attempt can legitimately commit code that doesn't parse.

Output: upserts one entry into that slice's cumulative scoring sheet (§7), keyed by the monotonic event-derived attempt ordinal (`bench_lib.attempt_ordinal` — never PM's own `attempts` counter, which resets to 0 whenever a stopped slice is restarted and so cannot be a stable key).

### Tools 2/3 — `review_score.py --skill drift-audit|code-review`: harvest, not invoke

One script, parameterized by which report it's reading (drift-audit and code-review harvesting are identical logic against two report shapes). It extracts deterministic structure from a commissioned reviewer's report — findings by severity, per-section item counts, the verdict, how many findings survive into the next *reviewed* attempt — never a holistic "how good was this review" score, which has no ground truth to check against. Reads the report only after verifying its recorded sha256 against `run.json`'s entry (the in-worktree mirror copy is written non-atomically, so file-existence alone isn't a safe read signal).

**One record per commission, never one slot per role.** Each attempt entry carries a `reviews` list, one record per successful commission, keyed on the commission's own `events.jsonl` index. That index, not PM's `review_id`, is the key: trials 4–7 carry no `review_id` at all, and where it exists it is only unique *within* a slice (Slice 1 and Slice 2 each have their own `review-1`). `review_id` is still carried verbatim on every record, so Tool 4 can join PM's own judgments on it. Two reviewer models commissioned against one submission are a genuine **panel** — two records, neither overwriting the other. A re-commission of the *same* reviewer against the same attempt (identical `(skill, tool, model, effort)` **lineage**) is a **retry**: the earlier record stays on the sheet marked `superseded_by` the later one's event index, so a retry never earns a second vote and a failed review never vanishes. `open_after_this_attempt` carries over per lineage, never per skill alone — mixing two reviewers' findings into one survival count would be meaningless.

Fully idempotent and re-derives its full commission set from the event log every call, so it is always safe to re-run: it processes every commission independently, skipping (and reporting, not raising for) an attempt with no sheet row to attach to rather than aborting the whole harvest at the first one found.

The finding parser accommodates exactly the four numbered-line shapes measured across all 144 reviewer reports in trials 4–14 — plain `[P1] …`, bold wrapping the whole finding, bold around the severity token alone, and a severity carrying a comma-delimited annotation inside the same brackets (`[P2, dissent from the named PM adjudication] …`, which trials 12–14's new reviewer models introduced). The annotation is swallowed and discarded: it is prose the reviewer attached to the severity, not a second severity, so accepting it never weakens the rule that a `P0-3` token must lead the bracket. The parser recovers a location only from a backticked span that is genuinely path-shaped, so a backticked attribute name (`redshift`) or function name (`_load_pair_counts()`) is never promoted to a file path. A finding with no recoverable location records one **explicitly absent**, never invented. Severity is always required: a numbered line with no `[P0-3]` stays a named parse error. The drift verdict is matched with Markdown emphasis stripped and its bullet dash optional (real reports write it bulleted-and-bold, bold-with-bold-token, and wholly inside one bold span); a report that genuinely contains no verdict at all stays a named parse error, which is the honest reliability outcome. **Four of the cohort's 144 reports remain named parse errors, and all four are reviewer-side, not parser-side.** Three never produced a report body at which a verdict or a finding could be looked for, and fail on the missing required sections: a drift reviewer that returned a single line asking for file permissions (trial 11), and two copilot-run code reviews that emitted only the harness's own progress narration (trial 13). The fourth is a code review whose Findings section is coverage prose carrying no severity token on any line (trial 14), where "severity is always required" correctly refuses to invent one. None of the four is a readable report the bench failed to read.

Widening the parser has never renumbered or re-titled a finding that already parsed, and this is re-proved on each widening rather than assumed: stage 4's three-shape widening left all 53 previously-parsing reports byte-identical, and stage 5's fourth shape left all 139 previously-parsing reports of the 144 byte-identical, changing exactly the one report it was written for. That invariant is what protects `finding_identity` and therefore every `open_after_this_attempt` count.

### Tool 4 — `model_report.py`

Gathers one model's full run into a per-model report: reads every `slice-<N>.json` sheet under `results/runs/<run_id>/` and reshapes them into one document — first- and final-attempt correctness/quality/scope/size-complexity and attempt count per slice, a compact per-attempt trajectory, and every review commission (`reviews`, one entry per commission — a panel or a retry both represented, never collapsed). It invents no new scoring math and no composite score (that is Tool 5's job, driven by `policy.yaml`); every field is a direct pass-through or reshape of data `dev_check.py`/`review_score.py` already computed. `correctness`'s bulky per-node `by_node` map never travels through this pass-through — it is stripped from `first_attempt`, `final_attempt`, and every trajectory row (see §7's `by_node` entry). In its place, each slice entry carries one `first_attempt_node_outcomes`: the first attempt's own `by_node` map, nested `{group_id: {node_id: outcome}}` by reusing `dev_check.py`'s own obligation-group map rather than a second implementation of it, and validated to reconstruct `by_obligation`'s recorded passed/total exactly, group by group, before being trusted.

It also harvests **PM's own structured judgments** from the same `--run-dir` it already reads for `timing`/`provenance`, through `bench_lib.active_judgments` (so a superseded judgment is never counted): `review_judgments` join onto this report's own `reviews` entries by `(run_id, slice.id, review_id)` as a `pm_rating`, and `developer_judgments` join onto the attempt trajectory by `(run_id, slice.id, submission.origin_event.index)` as a `pm_developer_judgment`. The Developer join converts that absolute event index to the bench's own attempt ordinal via `bench_lib.attempt_ordinal(..., before_index=index + 1)` — the `+1` makes the window inclusive of the origin event itself, which *is* the launch-family event that opened the attempt being judged; the strict form would resolve to the previous attempt, or raise outright when the origin event is a slice's only launch-family event. The harvest lives here rather than in `review_score.py` deliberately: judgments are per-slice run-level data spanning both reviewer skills *and* the Developer, and `review_score.py` is invoked once per `(slice, skill)` with no Developer-judgment concept at all. Validation is loud — an unknown `review_id`, a duplicate rating, a rank group naming a review that does not exist, a `skill` disagreeing with the joined review's own, or an `origin_event` that is not a launch-family event is a named problem, never a silently dropped judgment. A review or attempt PM never rated is **explicitly unjudged**, never inferred: `pm_lib` refuses historical backfill by construction, so a gap there is a real gap.

It also folds in PM's own `rate --text` comparative rating (`model-performance.md`, referenced by each sheet's `pm_model_performance_ref`), read back verbatim into a `pm_subjective_rating` block — kept **strictly separate** from the deterministic scores, never parsed into structured numbers, and never blended into them. The two signals differ in repeatability (the deterministic scores are comparable across runs; PM's rating is a within-run judgment call) and averaging them would destroy that distinction silently. A rating never recorded is an honest `available: false`, not an error; a rating recorded but since vanished from disk is a named problem.

Writes `results/runs/<run_id>/model-report.json`. Sheets that disagree on `model`, `run_status.pm_status`/`.stop_reason`, or a non-null `pm_model_performance_ref` are refused outright — these all come from the same run.json, so disagreement is corruption, never something to average or guess past.

### Tool 5 — `leaderboard.py`

Rebuilds the cross-model summary from every Tool 4 report on disk (`results/runs/*/model-report.json`), grouped by each report's own resolved Developer `configuration_key` (model · harness · effort — a configuration can have several runs on disk; `policy.yaml`'s `repeats` documents this). Only **attributed** reports are ranked; an unattributed run stays fully visible in the run index and its own detail section, and is never allowed to become a model named `None`.

**Ranking is mean first-attempt correctness, and nothing else.** There is no composite score: the four-term weighted blend this section previously described was deleted outright (`docs/LEADERBOARD-REBUILD-PLAN.md` Stage 2), along with its `weights`/`scope_violation_penalty`/`iteration_reference_attempts` policy keys, because two of its four terms were saturated at 1.0 on every stored attempt and a third could not distinguish one attempt from three. Per slice, correctness is the equally weighted mean of the final (or first) attempt's own obligation-group `fraction`s — never the raw `hidden_tests_passed/total`, which would double-count a large group, since the obligation partition *is* the rubric weight (`AGENTS.md`). That is averaged equally across a run's two slices, then equally across the configuration's *eligible* runs. A tie on exact first-attempt correctness breaks by smaller first-attempt production ΔLOC, then by `configuration_key`, and every tied pair is labelled `tied_with_previous` so neither tie-break reads as evidence.

Everything else is a **supporting column, never blended into a number**: final correctness, paired-run gain in percentage points (computed within each paired run first, then summarised), ΔLOC and ΔCC per slice, attempts, steers, PM elapsed time, and PM's own subjective rating carried through per run verbatim. Spread is reported as `mean [min-max], n` throughout; at n=1 the single value is shown with `n=1`, never a fabricated zero spread. Lint and code-health survive as a **hygiene and tool-coverage badge** rather than a score, and scope violations are an exceptions list in run detail with a document-level alert when any run has a nonzero count. A slice with no available measurement renders `unavailable`, never a fabricated 0. PM-run data only — there is no one-shot pre-filter screen feeding into this (§8).

Writes `results/leaderboard.json` (per-configuration ranking, unattributed runs, per-run coverage/eligibility, and the `measurement_metric_version`s in play) and `results/leaderboard.md` — four tables in fixed order (Developer first submission; Developer supervised outcome, in the *same row order*, never re-ranked; code reviewer — PM-assessed utility; drift reviewer — PM-assessed acceptability), then per-configuration detail, a run index anchored stably on run id so a rank change never breaks a link, measurement notes, and data problems stored once with their run reference. Machine attempt ordinals stay 0-based everywhere in the sheets and JSON; `_display_attempt` is the single boundary that converts to the 1-based number a human reads. `render_markdown` invents no new number; it only formats what `leaderboard.json`/`model-report.json` already contain.

### Tool 6 — `cohort_run.py`: operator convenience wrapper

Not a scoring tool — it invents no measurement of its own, reads no `run.json`/`events.jsonl`, and computes nothing Tools 1-5 don't already compute. It exists only to remove hand-assembly and hand-sequencing around them, and it must never grow a code path that crosses the boundaries §2 states: it never launches PM, never writes into a Developer/PM directory, and never touches a run in progress.

- **`setup`** creates a fresh trial worktree of `policy.yaml`'s `relative_velocity_repo` (unless `--repo` is given) and prints project-manager's own launcher prompt for it (§4 step 1), ready to paste. Creating/removing a worktree of the substrate repo is not "launching PM" or "adding to its prompt" (§2) — it is ordinary git housekeeping the operator would otherwise do by hand before pasting the prompt into their own harness. `relative_velocity_repo` defaults to `substrate/relative-velocity`, a local clone vendored under this bench's own repo root (gitignored) so trials are self-contained and immune to the operator's own working checkout of `relative-velocity` moving, being on the wrong branch, or having uncommitted changes; a relative `policy.yaml` path resolves against this bench's own repo root, never the caller's cwd. The worktree is created on branch `<dev_branch_prefix>/<label>` (default `pm-eval-v2`), checked out from this bench's one pinned plan commit — parsed live from `docs/MERGER_RATE_PLAN-2SLICE.provenance.md`'s own "Pinned commit" line, never a second, driftable copy of that hash — under `dev_worktree_root` (default: a sibling directory of `relative_velocity_repo`, i.e. also under `substrate/`). `--label` names the trial explicitly (refusing, by name, a collision with an existing branch or worktree directory); omitted, it auto-numbers from a fixed `trial` base so repeats never collide. The prompt text itself is extracted live from `SKILL.md`'s own `## Launcher` fenced block (via `policy.yaml`'s existing `pm_scripts_dir`) every time this runs, never a copy kept in this repo — the launcher's *wording* isn't something this bench scores (unlike the frozen plan, G8), so a stale local copy could only mislead an operator about what project-manager currently asks for. Only `Repo:`/`Plan file:` are substituted, from the created worktree unless `--repo`/`--plan-file` override them; `Developer:`/`Reviewer:` are always left exactly as the template states them (each with its own bracketed placeholder) — who plays either seat is the operator's own choice made in the pasted prompt, and this tool carries no flag for either (matching `policy.yaml`'s own comment on why there is no reviewer-seat key). The printed follow-up steps substitute the real `--dev-repo`/`--label` values `setup` already knows rather than leaving them as placeholders to hunt down. `--harness <codex|claude|copilot|opencode|qwen>` (optional) pre-registers the new directory as trusted for that harness in its own on-disk trust/permission store, so it doesn't prompt on first launch there — verified directly against each tool's real local config rather than guessed: Claude Code (`~/.claude.json`'s `projects[<path>].hasTrustDialogAccepted`), Codex CLI (`~/.codex/config.toml`'s `[projects."<path>"] trust_level`), and GitHub Copilot CLI (`~/.copilot/config.json`'s `trustedFolders` array) each get a careful, atomic, merge-only write (existing content and sibling entries always preserved). OpenCode keeps its equivalent state in a live, actively-written SQLite database with no documented safe external-write path, and no persistent per-directory trust store was found for Qwen Code at all — both are named as unsupported rather than silently skipped. This flag is never filled into the printed `Developer:`/`Reviewer:` lines; it exists solely for this pre-registration.
- **`analyze`** runs `grade_run.py` → `model_report.py` → `leaderboard.py` against one finished run (§4 step 3), in-process (each tool's own `main(argv)`, the same in-process-call pattern `grade_run.py` already uses for `dev_check.main()`), never as subprocesses. `--run-dir` names the run directly; `--dev-repo` resolves it via `git rev-parse --absolute-git-dir` + `/pm/` (§4's own resolution recipe), refusing by name, never guessing, if more than one run directory exists there. A step's own refusal (its `bench_lib.BenchLibError` subclass) is caught, reported, and does not stop a later step from running — `model_report.py`/`leaderboard.py` still operate correctly on whatever other data already exists on disk even when this run's own grading failed. The command's exit code is the max across every step it ran.
- **`cleanup`** removes a trial's worktree (never its branch — cheap, recoverable history left in place, per `AGENTS.md`'s "archive, never delete" spirit) via `git worktree remove`. `--label` scopes to one trial; omitted, every worktree under `dev_branch_prefix/*` is targeted. Dry-run by default; `--yes` actually removes; `--force` passes through to `git worktree remove` for a dirty worktree. An ungraded trial (no `model-report.json` recorded for any PM run found in it) is flagged with a warning, never refused outright — the operator may deliberately not want to grade every trial, an explicit operator decision this tool does not second-guess.
- **`reset-leaderboard`** archives (`AGENTS.md`: "archive, never delete") this repo's own regenerable `results/` output into a dated `archive/results-<UTC timestamp>/` directory (or one scoped to a single `--run-id`), so a fresh cohort pass can start clean without losing any prior run's evidence. Dry-run by default — nothing moves until `--yes` is given.

Field notes:

- **Key**: `(run_id, slice_id, attempt)`. `attempt` is `bench_lib.attempt_ordinal`'s value — the count of `launch`/`relaunch`/`steer` events recorded for the slice, minus one; 0-based, and monotonic across a stop/restart cycle (a restart's plain `launch` event counts the same as a `relaunch` would have). `pm_attempts_counter` is PM's own, separately-tracked, non-monotonic counter, recorded for cross-referencing PM's own output — never the key.
- **`provenance`** is captured once, at an attempt's first grade, and never rewritten on a regrade — so a `policy.yaml`/`obligations.yaml` edit made between two attempts cannot silently make an earlier attempt look graded under different rules. `obligations_hash` covers only the obligation *partition* — the rubric's weighting — not the hidden test bodies themselves, which are the rubric's actual content; an edit to a single assertion in a hidden test file changes every attempt's recorded correctness score without changing the partition at all. `hidden_tests_hash` (`dev_check.hidden_tests_manifest_hash`) closes that gap by hashing exactly the hidden test files `run_hidden_tests` copies into the grading worktree for that slice. A hand-maintained "correctness metric version" was considered and rejected in its place: a content hash cannot lie, whereas a version can be bumped for a comment-only edit or left stale across a material one, and since such a key would live in `policy.yaml`, bumping it would already change `policy_hash` — it would add no detection capability, only a second source of truth. Because `provenance` is never rewritten on a regrade, `hidden_tests_hash` appears only on attempts graded into a *fresh* scoring sheet; a cohort regrade in place leaves historical attempts without it, which is why a cohort regrade archives `results/` via `cohort_run.py reset-leaderboard` and regrades into a clean tree.
- **`pm_decision`** is read per attempt from `events.jsonl`, never from `run.json`'s one decision-per-*slice* field (which would flatten a steered first attempt and an accepted third attempt to the same value). `null` means undecided, never "nothing happened."
- **`run_status`** matches `pm.py`'s actual state machine: `run.json["status"]` has exactly four values, a slice's own `status` has exactly four. There is no distinct `attempt_budget_exhausted` state (it's `needs-human` + a `stop_reason` string) and no structured `infrastructure_failure` state in `pm_lib` at all — `infrastructure_failure_suspected` here is a heuristic this repo's own tooling would have to compute (not yet built), never a value read from PM.
- **No invented composite score** anywhere — not at the per-attempt level, and (since `docs/LEADERBOARD-REBUILD-PLAN.md` Stage 2) not in Tool 5 either. Per-attempt data is raw and diagnostic; Tool 5 ranks on first-attempt correctness alone and shows everything else beside it.
- **`reviews`** is one record per review *commission*, keyed on `event_index` (the commission's own position in `events.jsonl`) — never on PM's `review_id`, which trials 4–7 do not record at all and which is only unique within one slice. `review_id` rides along so Tool 4 can join PM's own `review_judgments` on it. Two reviewer models on one submission are two records; a re-commission of the same `(skill, tool, model, effort)` lineage is a retry, and the earlier record stays with `superseded_by` set rather than being overwritten — a retry must never earn a second vote, and a failed review must never disappear. There is no `commissioned` flag: every entry in the list *is* a commission. `open_after_this_attempt` carries over per lineage, and stays `null` (never `0`) until a successor commission of that same lineage exists to say whether a finding survived.
- **`size_complexity`** records `baseline_commit` per attempt on purpose: it is what lets Tool 4 detect a grading-baseline reset between a slice's first and final attempt (a stop/restart mid-run) and label that slice's first-to-final size comparison as unreliable, rather than reporting the difference as an apparent improvement. Correctness is measured per attempt and is unaffected. `metric_version` (from `policy.yaml`'s `measurement` section) travels with every block, so a metric-version rebuild of already-graded runs is distinguishable from a genuinely new trial.
- **`loc.production_categories`** (Stage 4) reclassifies the **production bucket only** of the physical ΔLOC directly above it into `code`/`docstring`/`comment`/`blank` — never test or doc, because the need this responds to is judging economy of *implementation*, never of tests or prose. `docstring` means an AST docstring specifically: the first statement of a `Module`/`ClassDef`/`FunctionDef`/`AsyncFunctionDef` body, when that statement is a bare string constant; a string constant anywhere else in a body is `code`. The four categories' `net` values always sum, exactly, to `buckets.production.net` on the same attempt — `dev_check.decompose_production_categories` asserts this reconciliation and raises loudly (naming both numbers and the files involved) rather than publishing a silently-wrong number if it ever fails. `available: false` (with a named `error`, never zeros) means a production file in this diff was binary, or failed to parse/tokenize at either revision — a Developer attempt can legitimately commit code that doesn't parse, so this never aborts the rest of grading.
- **`by_node`** is the full `node_id -> "passed"|"failed"|"error"|"skipped"` map `by_obligation`'s group counts were computed from, sorted by node id so regenerated sheets diff cleanly rather than reordering on every regrade. It exists so that "which hidden test drove this difference between two models," "is this obligation group saturated across the cohort," or "what would the ranking be under a different partition" are answerable straight from `results/runs/<run_id>/slice-<N>.json`, instead of requiring a re-grade of every run in fresh git worktrees. The full per-attempt map itself stays sheet-only, never threaded into Tool 4 (`tools/model_report.py`) or Tool 5 (`tools/leaderboard.py`) — `model-report.json` already runs to thousands of lines per run. What *does* travel onward is one map per slice, `first_attempt_node_outcomes`: the first attempt's `by_node`, nested `{group_id: {node_id: outcome}}` (reusing `dev_check.py`'s own `obligation_groups_for_slice`/`node_to_group_map` rather than a second rubric-map implementation) — for the rank-support diagnostic that needs to know which group's denominator a node counts against, not a second copy of the whole map.
- The number of `attempts` entries before `accepted_at_attempt` **is** the iteration-count metric. The sequence of `correctness`/`quality` values across the attempts that got graded **is** the trajectory — see §5 for which attempts that includes.

## 8. Known limitations and open questions

- **G1 — Review-quality scoring has no ground truth.** **Resolved, and now actually built** (`docs/LEADERBOARD-REBUILD-PLAN.md` Stage 4): a deterministic coverage proxy (Tools 2/3, above) plus PM's own judgment (Tool 4's harvest of `review_judgments`), kept strictly separate and never blended. PM supplies two independent signals — a 0–2 rating per report, and a best-first `rank_groups` comparison of a panel — and Tool 5 renders them as two tables, never as one number. Normalized rank points are `(N-r)/(N-1)` for a panel of N at 1-based rank r, ties sharing the mean occupied rank; **N = 1 has no comparative score at all, never a fabricated 1.0**. Bradley–Terry / Plackett–Luce were considered and rejected: not worth their identifiability and sparse-data cost at this sample size. One honest limit stands, and one has since been retired by data. The retired one: **every panel in trials 4–11 was a singleton** — grouping every review by `(slice, head, skill)` yields exactly one `(tool, model)` pair in every group — so the comparative column read "single reviewer — no comparative score" on every row, which was the cohort's real shape rather than an empty or broken table. **Trials 12–14 changed that**: they commission four distinct code-review models per submission, with real `rank_groups` comparisons including tie groups, so the code-review table now carries genuine normalized rank points. The drift-audit role remains a singleton across the whole cohort. Because a cohort's panel shape evidently changes underneath this document, the renderer no longer asserts it as a fixed fact — the prose in `leaderboard.md` is derived per role from the rows actually being rendered, so it cannot go stale the way this paragraph did. The limit that does still stand: normalized rank points do not correct for opponent strength, so reviewers in disconnected comparison groups are marked not globally comparable rather than silently ranked against each other.
- **G17 — Panel-preserving review records. Resolved** (`docs/LEADERBOARD-REBUILD-PLAN.md` Stage 4). The per-attempt `drift_review`/`code_review` single slots silently kept only the *last* review per `(attempt, skill)`, so a genuine two-model panel would have collapsed to one with no record the other existed, and a retry overwrote its predecessor outright. Both are now one record per commission in an attempt's `reviews` list (§7). This was not purely theoretical even in a cohort with no real panel: trial 11 slice 1's drift-audit attempt carries a failed one-line report immediately followed by a successful re-commission of the same reviewer, and the old design discarded the failure entirely — losing exactly the reliability evidence PM itself recorded, in its own `status: "unavailable"` judgment naming that review. A retry is now retained and marked `superseded_by`, so it never earns a second vote and never vanishes.
- **G19 — A comparison round must resolve reviewer identity, not scoring-sheet coverage. Resolved** (`docs/LEADERBOARD-REBUILD-PLAN.md` Stage 5). A rating and a comparison need different things from a `review_id`: a rating must find this report's own harvested `reviews` entry, because that is the record it attaches `pm_rating` to; a comparison needs only the reviewer's *identity*, to award rank points. Resolving both through harvested records alone meant a comparison silently lost members whose attempt was never graded. Trial 13 Slice 1 is the real case — its G16 walk was refused, so the earlier of its two four-way comparison rounds lost all four members and the round vanished, scoring those reviewers over three of PM's four comparisons and letting a *Developer* property (commit habits) contaminate a *reviewer* metric. `_resolve_comparison_member` now reads identity from `run.json`'s own `slices[].reviews[]`, which records `tool`/`model`/`effort` for every commission PM ever made, independent of grading coverage. The join key is unchanged — still `(run_id, slice.id, review_id)`, never list position, model, or artifact content. Dropping members one at a time was the worse failure of the two: it renormalizes `(N-r)/(N-1)` over a panel size PM never compared at, fabricating rank points; a member is now unresolvable only when PM's own state never recorded that review, which is a real error and reported as one. Verified by recomputing every comparative score independently from `run.json` and matching the rendered table exactly.
- **G20 — A dangling judgment join must name which of its causes applies. Resolved** (`docs/LEADERBOARD-REBUILD-PLAN.md` Stage 5). The unresolved-`review_id` message offered the reader a disjunction the tool could resolve from state it already held ("either PM recorded a review this report never harvested, or that review's attempt was never graded"), which is failing loudly but *unspecifically*. It now distinguishes three structurally determined outcomes: an ungraded attempt (a coverage gap, named with the attempt ordinal), a graded attempt with no harvested record (a genuine harvest anomaly), and a `review_id` absent from `run.json` entirely (PM naming a review its own state never produced), plus a named fallback when the ordinal cannot be resolved at all rather than assuming the benign case. The message states the observable fact and points at `grade_run.py`'s own output for the cause — it never asserts a cause it only inferred.
- **G18 — PM judgment consumption. Resolved** (`docs/LEADERBOARD-REBUILD-PLAN.md` Stage 4). `project-manager` now persists structured `review_judgments` and `developer_judgments` (`ai-agent-coder` `d7307dd`, `b9c10f4`, `04f3b86`), including an immutable `developer: {tool, model, effort}` snapshot that G-less earlier runs had no equivalent for. Tool 4 joins them structurally (see its §6 entry for the join keys and the `+1` ordinal conversion) and Tool 5 displays them in their own labelled columns and tables. They enter no deterministic number, by the same repeatability argument that keeps `pm_subjective_rating` separate. The `developer_judgments` snapshot additionally resolves the Developer-identity defect structurally rather than by operator attestation, for every run that has one (Stage 1; `bench_lib.resolve_developer_identity`).
- **G2 — PM's own acceptance judgment is unscored.** Accepted as a scope boundary: PM is presumably a strong frontier model, and this study is about the Developer seat. A future "which model makes the best PM" study would need different instrumentation.
- **G3 — Deterministic quality (lint/code-health) is an imperfect proxy for real code quality.** **Resolved** (`docs/LEADERBOARD-REBUILD-PLAN.md` Stage 3): it was worse than imperfect, it was vacuous. `run_code_health` synthesized `verdict = "pass"` from exit 0 even though `health.py` emits no verdict of its own, so a slice carrying ten code-health candidates scored a clean 1.0, and every one of the 28 stored attempts scored quality 1.0. The synthesized verdict is now `"measured"` — the honest reading of exit 0 is that the tool ran and produced a payload — and it is displayed as a hygiene/coverage badge, never scored. Its place in the ranking is taken by two measurements a reader can argue with, ΔLOC and ΔCC (Tool 1, §6), which are shown as supporting columns and never blended into a number.
- **G6/G7 — One-shot pre-filter screen. Dropped, not built.** A cheap pre-screen before committing a model to a full PM run was considered and rejected: a candidate model is only ever run through PM because the operator already cares about it, so the screen would never change that decision.
- **G9 — Grading-worktree discoverability by a live Developer session.** Not a live concern: grading strictly follows a run's end, so there is never a live Developer session left to discover a grading worktree, under any containment choice.
- **G12 — Containment/state-access backend.** `policy.yaml`'s `backend` key supports `local` (direct filesystem/subprocess) today; `sbx` (for an `ai-agent-sbx`-contained PM run) is reserved but not implemented — selecting it fails loudly rather than silently falling back.
- **G16 — Superseded-attempt grading (§5's scope limit). Resolved, via approach 1 (the git-log walk).** Every attempt of a slice now gets a deterministic grade (hidden tests/lint/code-health/scope) whenever `resolve_attempt_commits` recovers exactly one commit per attempt between the slice's own before_head and its final commit — no change to `project-manager`/`pm_lib` needed, and retroactive: it works on any already-recorded run, not just future ones. Validated against the real completed run on disk (`results/runs/20260911T112036Z-cd15fe/`: Slice 1's 5 attempts and Slice 2's 2 attempts both fully recovered, commit-for-commit, with correct per-attempt review harvesting) and against a synthetic stop/restart case built in a throwaway repo (a `finalize --stop` followed by a later plain `launch`, spanning two epochs, still recovers all 3 attempts intact).

  This relies on the Developer contract's one-commit-per-attempt convention, not a mechanical guarantee `pm_lib` enforces, so `resolve_attempt_commits` is a named refusal whenever it doesn't hold exactly (a merge commit in the range, a before_head that isn't an ancestor of the final commit, or a commit count that disagrees with the attempt count) — never a partial or guessed mapping. A subtlety the restart validation surfaced directly: the walk must start from the slice's *original* before_head (the previous slice's own recorded commit, when one exists), not from whatever `dev_check.resolve_before_head` would return for grading a single already-decided attempt — that function deliberately prefers the *most recent* epoch's before_head, which would silently truncate a multi-epoch slice's walk to only its last epoch. `_resolve_slice_before_head_for_walk` (`tools/grade_run.py`) makes this correct for any slice after the first, regardless of how many epochs it went through. A genuinely multi-epoch *first* slice still falls back to grading only its final attempt, with the refusal reported as a named problem, not a bug — regardless of whether an early (pre-restart) epoch's own review was ever recorded: `resolve_before_head`'s rule 4(b) can only ever select the review whose `head` matches the slice's *final accepted* commit, never an earlier epoch's, so there is no predecessor's commit to fall back on and no other structural source for the first slice's true earliest before_head.

  Approach 2 (extending `pm_lib` to persist each attempt's own commit/before_head directly) remains a fallback option if the git-log walk's convention-reliance ever proves too fragile in practice, but was not needed.

## Appendix: design history

Kept for context; not required reading to work on this repo. See `HANDOFF.md` for session-by-session detail and `git log` for the full trail.

This repo replaced two prior attempts at the same question: five one-shot tasks that tested a proxy (cheap one-shot quality predicts iteration-need) but never validated it against a real PM run, and a "Mode 1 + Mode 2" design that never reached a single real data point and, on inspection, measured nothing about iteration count or per-attempt trajectory — it scored a finished diff once, same as Mode 1. This branch (`pm-eval-v2`) started from an orphan root, carrying forward only the frozen plan, the pinned substrate, and the hidden-test content.

The grading design itself was rebuilt once, after real use. The original design had a driver (`tools/run_seat.py`) watch a PM run *live*, on the theory that a slice's base commit and a superseded attempt's own commit would become unrecoverable once PM moved past them. Running that driver against an already-completed real PM run exposed two bugs — an infinite loop in its terminal-status check, and a `before_head` that could never be resolved for either slice's final attempt — and the investigation into the second one showed the underlying theory was wrong: both facts are permanent and structurally recoverable from `run.json` alone, verified directly against `pm_lib` source, not merely reasoned about. The live-watching driver was retired and replaced by the single-pass `tools/grade_run.py` design in §5. Two independent reviews of that redesign then found (and fixes closed) a real data-loss bug in review harvesting — an earlier attempt's missing sheet row was silently discarding a *later*, gradeable attempt's own review data too — plus several narrower correctness edges in the structural `before_head` resolution. The one-shot pre-filter screen (G6/G7) was dropped in the same session, on the operator's direct judgment that it never changed which models got a full run.
