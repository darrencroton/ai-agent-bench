# Mode 2 Rewrite Plan: PM-Only Evaluation, Minimal Repo

**Status: in build on `pm-eval-v2`. §10 steps 1-9 are done — the obligation partition, `policy.yaml`, Tool 1 (`tools/dev_check.py`), Tools 2/3 (`tools/review_score.py`), and the driver (`tools/run_seat.py`) all exist and are tested; Tool 1/2/3 are additionally validated against one complete, real PM Mode B run (step 8, 2026-09-11). Tools 4 and 5 do not exist yet. This document remains the complete brief — a fresh session should be able to work from this alone, without re-reading the full history of `eval-consolidation-trial` or `main`.**

## 1. Why this exists (short version — see `HANDOFF.md`'s "corrected theory of the case" for the full history)

This repo exists to answer one operational question: which local model should sit in the Developer seat for a real, supervised, multi-step `project-manager` run on production scientific code? Prior real-world use of `relative-velocity` showed local models converge to scientifically-equivalent code but differ a lot in final quality and how many review/fix iterations it takes to get there. That variance, under a real PM process, is the thing worth measuring — and it needs to be measurable repeatably and offline, not by using a model "in the wild" on real production code and hoping.

Two prior attempts did not get there:

- **The five one-shot tasks (001-005)** tested a proxy (one-shot quality predicts iteration-need) but never validated it against a real PM run, and never established whether the five tasks were redundant or covered real gaps.
- **This branch's Mode 1 + Mode 2 infrastructure** (profile view, structural scoring, fail-closed provenance) never got to a single real Mode 2 data point, and — confirmed by direct code inspection — measures nothing about iteration count or per-checkpoint quality trajectory anywhere. It scores a finished diff, once, exactly like Mode 1 does.

**Decision made this session: abandon that path. Start over on a new branch, scoped only to what this design needs.** Everything not needed for that is left behind — not deleted from history (it stays on `main` and `eval-consolidation-trial`), just not carried forward.

## 2. What this branch is for, precisely

Run the `relative-velocity` 2-slice merger-rate plan (`docs/MERGER_RATE_PLAN-2SLICE.md`) as a real, **completely normal, unmodified** `project-manager` Mode B session, rotating local models through the Developer seat under one (probably frontier) PM supervisor, with **deterministic scoring instrumentation that externally watches and harvests the PM toolkit's own artifact trail** — not a replacement for the PM skill's own workflow, and not instructions injected into the PM's own decision-making at all: the launcher prompt is `SKILL.md`'s standard, unmodified text (see §7 item 3, RESOLVED against `pm_lib`'s actual plan-risk derivation, not merely inferred: both slices' own frozen Risk Flags already mechanically require mandatory review without needing anything added to the prompt). The PM skill already runs Developer → review → accept/reject per slice and already writes a structured record of every attempt and review to disk; this repo adds four small scripts (one of which handles both review types, parameterized — see §7) plus a driver that reads that record as it's produced, so every iteration is scored, not just the final result.

This directly closes last session's biggest identified gap: because the scoring sheet is updated every time around the review loop, the **iteration count and the quality trajectory across iterations fall out of the data automatically** — that was the one thing neither Mode 1 nor the old Mode 2 ever captured, and it was the operator's original motivating observation about local models in production use.

## 3. Design principles (binding for the fresh session)

- **Minimum, no dead code.** Every file in the new branch must be load-bearing for running the 2-slice plan and scoring it. If a prior file's *pattern* is worth keeping (fail-closed scope checks, provenance hashing, externalized policy), reimplement it fresh and small — do not carry over a script written for a different purpose (five-task grading, one-shot batch running, composite scoring) and adapt it in place. This applies most strongly to Tool 1 below — it must be purpose-built for this single plan, not a repurposed `grade_trial.py`.
- **Deterministic first.** Correctness and quality should be measured by tools, not by asking a model to judge a model. Reach for an LLM judge only if a deterministic proxy is tried and found insufficient — do not pre-build judged scoring on spec.
- **Externalize policy as data.** Whatever weights, thresholds, or gates the scoring uses belong in a small policy file (YAML), never hardcoded in the tools. This is the one thing worth keeping from the old repo's philosophy regardless of the rewrite — it's cheap and it's correct practice, not scope creep.
- **Provenance on every record.** Every scored artifact should record: the plan file's hash, the policy file's hash, the base/frozen-substrate commit or tag it was checked out from, the PM skill version if identifiable, and the branch/commit SHA being scored. This is what lets a later comparison detect "the rules changed" instead of silently mixing incompatible cohorts.
- **Isolate every grading run in its own worktree; containment of the PM/Developer run itself is the operator's choice, not this repo's to enforce (RESOLVED, G12 — see §7a for the full design).** The dev-side tool will run many times against an evolving branch (once per review round); each run must check out the branch's current HEAD into a fresh, disposable worktree, never the PM's live working directory. `project-manager`'s own documentation notes a fully-autonomous Developer session can otherwise reach anywhere else on the host, hidden tests included, and recommends real container/VM isolation for that reason — but this bench is deliberately container-agnostic: the operator may run PM bare or under their own `ai-agent-sbx` workbench, and either way the driver's own state access goes through one small `local`/`sbx` adapter (§7a). Reimplement the worktree pattern minimally (don't drag over `worktree_lifecycle.py` as-is).
- **The PM skill's own workflow is out of scope.** This repo does not reimplement Developer/reviewer orchestration, slice sequencing, or acceptance logic — `project-manager` Mode B already does that. These five tools are instrumentation invoked at its checkpoints, nothing more.

No tool in this design requires `results/` to be git-tracked — Tools 4/5 read it straight off the local filesystem — so this is a pure operational choice with no consequence for correctness.

## 6. The scoring sheet artifact

One JSON document per (run, slice), appended to or updated across attempts — not overwritten, since the whole point is watching the trajectory. **Keyed by a monotonic per-slice attempt ordinal derived from `events.jsonl` — CORRECTED 2026-09-11 (this section previously said the key was PM's own `attempts` counter; that was wrong — see the restart-epoch correction below)**: the key is `(run_id, slice_id, attempt)`, where `attempt` is `tools/bench_lib.attempt_ordinal`'s value — the count of `launch`/`relaunch`/`steer` events recorded for that slice, up to and including the one that opened it, minus one. Both Tool 1 and Tools 2/3 call this one function, so they cannot disagree by construction (finding 2, codex/gpt-5.6-sol independent review). A watcher detects a new attempt safely by watching `events.jsonl` for a `launch`/`relaunch`/`steer` event on the slice and only then reading `run.json` — rotation of the previous attempt's files into `attempt-<n>/` happens *before* `run.json` is updated, which happens *before* the event is appended, so polling `result.json`/the slice directory alone risks reading mid-rotation. **The `<n>` in `attempt-<n>/` is PM's own, separately-tracked counter's *new*, already-incremented value minus 1** (both `start_slice`'s relaunch path and `finalize_steer` compute the rotation target as `attempts - 1` *after* incrementing `attempts` for the new attempt) — which numerically equals the superseded attempt's own prior count, so `attempt-<n>/` is named by the attempt it holds, not by the attempt that just started. A watcher locating a specific historical attempt's rotated files must compute `n` this way from PM's own counter (recorded on the sheet as `pm_attempts_counter`, see below), not from the sheet's key.

**Restart-epoch correction (2026-09-11, found reviewing an independent codex/gpt-5.6-sol review of Tools 1-3): `run.json`'s `attempts` counter is not a stable per-slice identity, and keying the sheet on it destroys trajectory data.** `pm_lib.slice_ops.start_slice` resets a slice's `attempts` to 0 whenever it is (re)started on the *non*-relaunch branch — which is exactly what happens after `finalize --stop` records the slice as `stopped` and clears `current_slice`, a human reviews it, and `start-slice` runs again: with no live `current_slice` naming this slice, `start_slice` takes the non-relaunch branch and sets `attempts = 0`, even though the slice may already carry several attempts from before the stop (verified directly against `pm_lib/slice_ops.py`'s `start_slice` and `finalize_stop`). Keying the sheet on that counter would have `dev_check.py` silently overwrite the earlier attempt-0 row the instant the slice restarts — destroying exactly the trajectory data this bench exists to capture — while `review_score.py`'s own attempt attribution (which already counted launch-family *events*, never read the counter, from its first build) would keep incrementing and disagree with `dev_check.py`'s key. The event log itself never resets: a restarted slice's next launch is recorded as another plain `launch` event for the same slice id (not a `relaunch`, since PM's own state has no live `current_slice` to relaunch), so counting those events monotonically produces a key that survives a stop/restart cycle intact. **The fix: key on `bench_lib.attempt_ordinal` (above), and keep PM's own counter only as a recorded field on the attempt entry, `pm_attempts_counter`** — what a human sees in PM's own output, never the sheet's key. Proposed shape (metrics are raw counts, not an invented composite — see the note after the schema):

```json
{
  "run_id": "...",
  "model": "opencode-go/mimo-v2.5-pro",
  "slice": 1,
  "run_status": {
    "pm_status": "active | needs-human | complete | stopped",
    "slice_status": "null | accepted | attested | stopped",
    "stop_reason": "... | null",
    "infrastructure_failure_suspected": false
  },
  "attempts": [
    {
      "attempt": 0,
      "pm_attempts_counter": 0,
      "commit_sha": "...",
      "timestamp": "...",
      "provenance": {"plan_hash": "...", "policy_hash": "...", "obligations_hash": "...", "base_commit": "...", "pm_skill_version": "..."},
      "correctness": {"hidden_tests_passed": 41, "hidden_tests_total": 46, "by_obligation": {...}},
      "quality": {"lint_findings_by_tool": {...}, "code_health_findings_by_category": {...}},
      "scope": {"violations": []},
      "drift_review": {"commissioned": true, "report_ref": "...", "report_sha256": "...", "findings_by_severity": {...}, "open_after_this_attempt": 2},
      "code_review": {"commissioned": true, "report_ref": "...", "report_sha256": "...", "findings_by_severity": {...}, "open_after_this_attempt": 1},
      "pm_decision": "steer"
    }
  ],
  "accepted_at_attempt": 3,
  "pm_model_performance_ref": ".pm/runs/.../model-performance.md"
}
```

**`pm_attempts_counter` and `provenance` moved to per-attempt fields (finding 4, 2026-09-11).** `pm_attempts_counter` is PM's own `attempts` value at grading time — the restart-epoch correction above means this is no longer the sheet's key, but it is still recorded, since it is what a human sees in PM's own output. `provenance` (`plan_hash`, `policy_hash`, `obligations_hash`, `base_commit`, `pm_skill_version`) used to be a single sheet-level field, overwritten on every upsert — which meant a `policy.yaml` or `hidden_tests/obligations.yaml` edit made *between* two attempts silently rewrote what an *earlier* attempt appeared to have been graded under, defeating §3's "detect the rules changed" requirement. It is now captured once, at each attempt's first grade, and never rewritten on a later regrade of that same attempt (`tools/dev_check.build_provenance`/`upsert_attempt`). `obligations_hash` is new: `docs/OBLIGATION-GROUPS.md` establishes that the obligation partition *is* the correctness rubric, so a later edit to it must be exactly as detectable as a policy or plan change. `report_sha256` on `drift_review`/`code_review` (finding 3) is the run.json-recorded hash of that review's report, kept so a later harvest of the same slice+skill can recognise an already-recorded review without re-reading its file.

**`pm_decision` is read per attempt from `events.jsonl`, not from `run.json` (2026-09-11, found while building Tool 1).** `run.json` records exactly one `decision` string per *slice*, so copying it onto every attempt entry would report the same value for the first attempt that was steered and the third that was accepted — flattening precisely the iteration trajectory §6 exists to capture. The event log carries the real per-attempt answer: attempt `n` opens at the (n+1)-th `launch`/`relaunch`/`steer` event for the slice and closes at the first following `steer`, `relaunch`, `accept`, `slice-stop` or top-level `stop`. An attempt with no such event yet records `null`, meaning undecided — never a decision it did not receive.

**`attempt` is 0-based**, matching `bench_lib.attempt_ordinal`'s count of launch-family events minus one: 0 at the first `launch`, and thereafter +1 per subsequent `launch`/`relaunch`/`steer` event for that slice — a restart's plain `launch` event counts exactly the same way a `relaunch` would have, which is what keeps the ordinal monotonic across a stop/restart cycle (see the restart-epoch correction above). An earlier draft of the example above showed `"attempt": 1` for the first entry, which contradicted this section's own keying note; corrected 2026-09-11. `accepted_at_attempt` is a value of the same ordinal, so a slice accepted on its first try records `0`.

**No invented composite score at the per-attempt level** (dropped `structural_score` from the first draft — codex's review correctly flagged it as an undefined conversion from raw lint/code-health output). Per-attempt data is raw and diagnostic; any weighting into a single number happens only in Tool 5's leaderboard pass, driven entirely by `policy.yaml`, never invented ad hoc inside Tool 1.

**`run_status` is mandatory, not optional, and RESOLVED, G14, against `pm.py`'s real state machine — which is smaller than the first two drafts assumed.** `run.json["status"]` has exactly four values: `active | needs-human | complete | stopped`; a slice's own `status` has exactly four: `null | accepted | attested | stopped`. **There is no distinct `attempt_budget_exhausted` state** — budget exhaustion is `status="needs-human"` plus the literal `stop_reason` string `"attempt budget exhausted"` (a PM-initiated slice stop via `finalize --stop` is also `needs-human`, with PM's own free-text reason instead — the needs-human/stopped split is about *who* stopped it, an operator-issued top-level `pm stop` being the only path to `status="stopped"`, not about severity). **There is also no structured `infrastructure_failure` state — confirmed as a real gap in `pm.py` itself, not a research miss**: trust-dialog/harness-crash detection (`sessions.py`'s `scan_dialog_markers`) is surfaced only to stdout, never written to `run.json`/`events.jsonl`. So `infrastructure_failure_suspected` in the schema above is explicitly a **driver-computed heuristic** (e.g., a Developer tmux session that has died with no terminal event ever following it), never a value read from PM's own state — the driver must compute and set it itself, and must never let a run that's merely `needs-human` (a normal, informative PM decision) get miscategorized as an infrastructure failure or vice versa. This directly answers a lesson this repo's own prior history already learned the hard way (an overdue "systematic technical-failure rule" from the branch being superseded by this plan) — build it in from the start here rather than relearning it. One related resolved finding: every recognized terminal transition (`stop`, `finalize_stop`, `finalize_accept`, budget exhaustion) unconditionally regenerates `run-report.md` — Tool 4/5 do not need to defensively call `status --report` after a stop.

The number of `attempts` entries before `accepted_at_attempt` **is** the iteration-count metric. The sequence of `correctness`/`quality` values across them **is** the trajectory the operator wants to watch. `drift_review`/`code_review`'s `commissioned: false` (rather than a missing field) would record that PM chose not to commission review for that attempt — though for this specific plan, see §7: both slices' frozen Risk Flags mandate independent review on acceptance (confirmed directly in `references/run-state.md`'s Risk semantics: `plan_risk` is derived mechanically at parse time and `independent-audit: yes` always elevates it — RESOLVED, no longer pending), so `commissioned: false` is expected to be rare here in practice, and its presence in the schema is defensive, not evidence it's confirmed to never fire.

## 7. The five tools

**Design correction (this session, verified directly against `project-manager`'s own `SKILL.md` and `README.md` — the first draft of this plan was written one level of abstraction above where the PM toolkit actually operates, and a fresh-eyes review caught it):**

`pm.py` already writes a rich, structured artifact trail for every slice and every commissioned review, in two places: `<repo>/.pm/runs/<run-id>/slices/slice-<N>/` (the **live/current** attempt's `diff.patch`/`result.json`/`validation.md`/pane captures/`assessment.md` at the slice directory root, `review-<skill>-<tool>.md` + its `-prompt.md` for every commissioned review, and an `attempt-<n>/` subdirectory holding each **superseded** launch once a steer or relaunch replaces it) and `<git-dir>/pm/<run-id>/` (the authoritative originals, plus `notes.md`, `model-performance.md`, `run-report.md`).

**This changes the tools' job from "the PM actively invokes our scripts mid-workflow" to "our tooling externally watches and harvests the PM's own artifact trail as it's produced."** That is a better design on every axis that matters here: it doesn't depend on the PM correctly remembering to call unfamiliar tools at the right moments (a real reliability risk the first draft didn't account for); it doesn't require deviating from a normal Mode B run to force reviews that wouldn't otherwise happen; and it reuses the attempt/slice identity PM already tracks instead of inventing a parallel counter that the checkpoint tools would have to agree on independently.

PM runs `lint` and, when structure materially changes, `code-health` itself as part of its own assessment — but only as prose narration ("say in the assessment that you did"), with no guarantee of machine-readable counts. **Tool 1 does not harvest these from PM's assessment; it always invokes them independently and directly** (below) so every attempt of every model gets the same, comparable, structured measurement — PM's own mention of them is qualitative color for Tool 4's report, never the numeric source.

**Codex's independent review (this session) confirmed two more errors in the first correction pass, verified against the actual `SKILL.md`/`README.md` text, and one real simplification opportunity. All three are fixed below:**

1. Current-attempt artifacts live at the **slice directory root** (`prompt.md`, `diff.patch`, `validation.md`, `result.json`, `assessment.md`); `attempt-<n>/` specifically holds **superseded** launches (`README.md`'s Layout section). The previous correction's trigger path (`.../attempt-<n>/`) was wrong for the live attempt.
2. `result.json` (the Developer's own artifact) is written *before* PM runs `finalize`, lint, code-health, and any review — so a single "harvest quality from the assessment" trigger conflated two different points in time. Quality must be computed independently and directly, not scraped from PM's free-text `assessment.md`, which is prose reasoning with no guaranteed structured numbers in it (`SKILL.md`'s Workflow step 3 only requires PM to *say* it ran lint, not to record parseable counts).
3. Both slices of the 2-slice plan declare `Independent audit required: yes` in their own frozen Risk Flags — **RESOLVED, G13: confirmed directly** against `references/run-state.md`'s Risk semantics ("`plan_risk` is derived mechanically at parse time (approval `yes`, independent-audit `yes`, or risky-surfaces ≠ exact `none` ⇒ `elevated`) and never changes"), not inferred from `SKILL.md` prose alone. Both slices are therefore mechanically elevated at parse time, which makes both drift-audit and code-review **mandatory on every acceptance regardless of Developer-model discretion**. The first correction's "tell the PM these are unproven models so it invokes standing-practice review" reasoning was solving a problem the frozen plan already solves on its own — delete it; it was itself a small piece of unnecessary complexity. Do not add anything to the launcher prompt to compensate for it either way.

### Tool 1 — `dev_check.py` (correctness; independent, always-computed quality)

**Trigger — RESOLVED, G13:** watch `events.jsonl` for a `launch`/`relaunch`/`steer` event on the slice, then derive the attempt number by counting launch-family events for that slice in the log (`bench_lib.attempt_ordinal`) — **not** by reading `run.json`'s own `attempts` count (finding 2, 2026-09-11): that counter is `pm_lib.slice_ops.start_slice`'s own state, reset to 0 whenever a stopped slice is relaunched, so it is not the monotonic key §6 requires; the event-derived count survives a stop/restart intact. Do not poll the slice-root `result.json`/`diff.patch` directly: rotation of the previous attempt's files into `attempt-<n>/` happens *before* `run.json` is updated, which happens *before* the event is appended, so a naive file-existence poll can read a partially-rotated state. See §6's schema note for the full key.

**Two refinements to that trigger, from reading `pm_lib/slice_ops.py` directly while building the tool (2026-09-11):**

1. **The watch loop lives in the driver (§7a) alone; Tool 1 itself is a pure, one-shot grading command the driver calls.** It is not idempotent in the strict sense — each grade stamps a fresh `attempt_entry["timestamp"]` (`utc_now_iso()`) even when re-grading the same attempt with otherwise-identical inputs, so byte-for-byte reruns are not expected; what is guaranteed instead is that every other field is either recomputed identically from the same recorded commit or, for `provenance`/`pm_attempts_counter`, preserved from the attempt's first grade (findings 2 and 4). Tools 1, 2 and 3 all trigger off the same `events.jsonl`; giving each its own watcher would be three implementations of one concern, against the DRY and minimum-code principles in §3. Tool 1 therefore takes an explicit `(run dir, slice, attempt, commit)` and grades it, which is also what makes it testable against synthetic fixtures before any real PM run exists.
2. **A `launch`/`relaunch`/`steer` event opens an attempt; it does not make one gradeable.** At launch the Developer has committed nothing yet. The event that marks an attempt's work finished and gradeable is `floor` (`kind: "floor"`, appended by every `finalize` — bare, `--steer`, `--accept` and `--stop` alike), at which point `diff.patch` is written and the repo HEAD is the attempt's commit. The launch-family events remain how the driver establishes attempt *identity*; `floor` is when it should call Tool 1. Note the floor report itself is never persisted in structured form — only a one-line note reaches `events.jsonl` — which is exactly why Tool 1 recomputes scope itself (below).
3. **Grading an accepted slice requires an earlier grade of that *same attempt* while it was still current (2026-09-11).** `finalize_accept` sets the slice entry's `status` to `accepted` and clears `current_slice` in one state write, and `before_head` is recorded *only* on `current_slice` — so after acceptance PM no longer holds the base commit anything is measured against. Tool 1 therefore falls back to the `provenance.base_commit` an earlier grade of that same attempt already wrote into the sheet (`tools/dev_check.resolve_before_head`, keyed by `attempt`, not merely by slice). This is deliberately narrower than "any prior grade of the same slice": a stop followed by a restart makes PM establish a brand-new `before_head` for the restarted slice, under a new, later attempt number (finding 2) — falling back to an *earlier* attempt's `base_commit` there would silently measure the restarted attempt against the wrong base. The consequence is a driver contract, recorded in §7a: grade at every `floor` event, and then once more after `accept` — never for the first time after acceptance, which fails loudly with no sheet to fall back on. Without this, `accepted_at_attempt` — which §6 calls the iteration-count metric, the single thing this branch exists to measure — is permanently unreachable.

**Correctness (the genuinely new work — PM has no reason to know about held-out tests):** check out the attempt's recorded commit into a fresh, disposable worktree (never PM's, the Developer's, or the Reviewer's own directory — a real enforced boundary if the operator runs under `sbx`, a convention only if run bare; see G12/G9), copy in that slice's hidden test file, run it, score pass/fail per acceptance-obligation group.

**Obligation groups — done, 2026-09-11**, re-derived against this plan's own Acceptance Criteria exactly as this section required, and living as data in `hidden_tests/obligations.yaml` rather than in Tool 1's code. Slice 1 has 6 groups over 44 nodes, Slice 2 has 4 over 17. The redundancy this section warned about was real and present in Task 001's map: input-validation guards were spread across three groups and dominated two of them, giving one capability roughly a third of Slice 1's weight. They are now a single group. Slice 2's two groups became four for the opposite reason — they were coarse enough to bury the plan's own stated "scientific assertion of the plan" at one seventh of the group it sat in. Full reasoning, and the rule that the partition *is* the rubric weight, in `docs/OBLIGATION-GROUPS.md`. **Corrected three times now.** First, for conflating the PM's own harness invocation with the Developer's. Second (independent Codex review), for a wrong claim about which sessions actually use tmux. **Third and most significant (this session, from a real empirical test, not a documentation re-read) — the driver does not launch the PM session at all. - **Driver contract: the scoring sheet has no lock.** Tools 1-3 each read-modify-write the same per-slice JSON document with a plain load/mutate/atomic-replace cycle and no file lock. This is safe only because the driver calls them serially, one grading step at a time, per slice — never two of Tool 1/2/3 concurrently against the same sheet. That is safe to require: `floor` and `review` are distinct, sequential events in PM's own event log, so there is never a real need to call two of these tools at once for one slice. A future driver may parallelize across slices that share no sheet, but never across attempts of one slice's sheet. This is a driver contract, not a lockfile — none is built here.
- **Driver contract: grade every `floor` event, and grade once more after `accept`.** Tool 1 can only recover an accepted slice's base commit from a sheet an earlier grade of that slice already wrote (see §7's Tool 1 note 3). A driver that waited for acceptance and graded once would fail loudly with nothing to fall back on, and one that stopped grading at the last `floor` would leave `accepted_at_attempt` and the final attempt's `pm_decision` null — losing the iteration-count metric §6 exists to capture.

**Built, 2026-09-11 (`tools/run_seat.py`).** A pure poll loop over `events.jsonl`/`run.json`, in-memory only (no watermark file — a restarted driver re-dispatches from event index 0). Went through **three** independent codex/gpt-5.6-sol reviews (medium effort, via `orchestrator`), each verifying the driver's own assumptions directly against `pm_lib` source rather than trusting this repo's comments — the first found four real defects in the initial build; the second, verifying that fix round, found one of those four fixes was incomplete in two further ways and the terminal-status fix was a heuristic, not real synchronization; the third, verifying that round, found the terminal-status fix could still stall behind an unrelated trailing event, pushed back on "grading failures are never retried" as too extreme, and found a malformed-state edge case. This session's own final self-review then caught two more subtle ordering bugs in the retry mechanism it had just added, before any of this was committed. The full, current design (see `tools/run_seat.py`'s own module docstring for the complete reasoning trail, not repeated here):

1. **Grading resolves an explicit `--commit`, and groups by (slice, attempt), not slice alone.** `dev_check.py` cannot check out anything but the Developer repo's current HEAD unless told otherwise, and PM's own `finalize --accept` clears `current_slice` and appends `floor` and `accept` back-to-back in one command — so a driver polling normally, not just recovering from a backlog, routinely sees both together. Only a slice's LATEST attempt in a batch is dispatched (an earlier attempt's own commit cannot be recovered from anything PM persists); every one of that latest attempt's own events is still dispatched, in file order. Once a slice is recorded `accepted` in `run.json`, its recorded `entry["commit"]` is passed explicitly, which stays correct no matter how far a *later* slice has since moved the repo's global HEAD — the actual fix for a backlogged, already-accepted slice, since HEAD is repository-wide, not per-slice. A malformed state (accepted with no recorded commit) is a named problem, never a silent HEAD fallback.
2. **The terminal-status check confirms the most recent *relevant* event, not simply the log's last line, is PM's own specific closing kind for that status.** PM saves `run.json`'s terminal status before appending the event that reflects it, so a fixed "same status twice" debounce is a delay, not synchronization — this driver instead waits however long it takes for the closing event to appear. Checking the literal last line broke on a trailing, unrelated event (e.g. `approve()`, which PM permits after a run is done) — the fix looks at the most recent event that is itself a tracked state transition, skipping anything else.
3. **A `stop` event's "slice" field reflects only whether a slice was current at that moment, not which kind of stop it was** (`pm_lib.slice_ops.stop`) — an operator's top-level `pm stop` and an attempt-budget-exhaustion stop carry the same shape; there is no need to tell them apart. A further, accepted limitation: a top-level stop does no floor/clean-worktree check, so it can grade an attempt that never itself committed anything (attributing an earlier commit to a newer attempt number) — not silent corruption, since the row's own `commit_sha` discloses exactly what was measured, but not fixed further this round.
4. **A failed grading dispatch gets exactly one bounded retry, on the next poll — not zero, and not unconditional-forever like review harvesting** (which stays cheap and fully idempotent, so re-deriving and re-attempting every known `(slice, skill)` target every poll is safe and is what recovers a review that raced ahead of its own floor event). Grading runs the full hidden-test suite plus lint and code-health — genuinely expensive — so it gets one retry, not infinite ones: dropped as superseded if a newer attempt appears first, given up on (logged) if the retry itself fails again. Getting "one retry, next poll" actually true (not just aspirational) required two more fixes this session found in its own work: retrying pending failures *before* dispatching a poll's own new events, so a fresh failure isn't retried moments later in the same call; and refusing to stop on a confirmed terminal status while a retry is still outstanding, since PM can append `floor`, `accept` and `complete` all before this driver's first poll ever runs.

Two findings are recorded as deliberate, named gaps rather than fixed (full reasoning in the module docstring): `infrastructure_failure_suspected` (§6's mandatory field) is never computed — detecting it is a genuinely new capability, not a light-touch fix; and `run.json["status"] == "stopped"` is this bench's own *operating assumption* of finality (matching the documented operator workflow), not a guarantee `pm_lib` enforces — `stop()` doesn't clear `current_slice` and `start_slice()` has no guard against it, so a `stopped` run could in principle be reactivated.

A single grading or harvesting failure is logged and does not stop the watch — `OSError` is caught alongside each tool's own named exception type. A corrupt `events.jsonl` line is fatal immediately, per `bench_lib.read_events`'s own contract. Tools 4 and 5 remain unbuilt — the driver prints that fact rather than calling scripts that don't exist. 138 tests pass (81 carried over, 57 for this module), lint clean.
